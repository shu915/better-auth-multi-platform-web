## 実行中のタスク
- feature/mobile-code-exchange(レビューの S3): マジックリンクで戻るディープリンクに、セッションを載せない。`expo()` は、リンクに `?cookie=<署名付きセッション>` を付ける(独自スキームは他のアプリも登録できるので盗まれる)。`mobileCodeExchange()`(src/lib/mobile-code.ts。`sessionRedirectPlugins()` で `expo()` の直後に置く)が、それを取り除いて、60 秒で失効する 1 回限りの `?code=` に置き換える。アプリは `POST /api/mobile/exchange`(`{code, verifier}`。src/lib/mobile-exchange.ts)で、PKCE(RFC 7636)の verifier を添えて、セッションに引き換える。`cc`(challenge)のないリンクにはセッションを渡さない(`?error=missing_challenge`)。コードは 1 回で使い切り、保存するのはコードのハッシュと、暗号化した Cookie と、challenge。拒否の理由は応答に出さず、ログにだけ出す(`[mobile-exchange] refused: …`)。本文は 2KB まで(バイト数で数える。`readLimitedText`)
  - 状態: 1 コミット済み(1b49b84)+ レビューの反映(暗号化して保存、本文の上限、足りなかったテスト)が未コミット。vitest 251 件、tsc、lint、build は通る。evaluator は合格(その後のレビューの指摘も反映)。iOS で、ログインの成功(`exchange 200`)と、同じリンクの再利用が失敗することを確認済み。Android も、JS を再読み込みしたあと、ログインできた。暗号化のあとの、もう一度のログインは、端末で未確認
  - **デプロイの順序**: 古いモバイルは `cc` を送らないので、この Web ではログインできなくなる。モバイル(mobile リポジトリの feature/s3-code-exchange)と同時に出す(開発中は問題ない)
  - 残る限界: 攻撃者が自分の `cc` を付けたログインメールを被害者に送らせ、被害者がそのリンクを開き、被害者の端末に攻撃者のアプリがある場合は、コードを取られる。Universal Links / App Links が要る(ドメインとストアの設定が決まってから)。別のアプリが、コードを横取りして、でたらめな verifier で先に引き換えると、本物のアプリのログインは失敗する(セッションは盗まれない)

## 既知の限界(許容している)
- ネイティブ(Expo)のマジックリンクは、独自スキームのディープリンクに、1 回限りのコードを載せて戻す(S3。上の実行中を参照)。独自スキーム自体の限界は残る(Universal Links / App Links が要る)
- Go API にレート制限がない。`/api/mobile/exchange` にもレート制限がない(コードが 256 ビットで当たらないため)。JWT は退会後も最大 5 分有効だが、Go が退会後 10 分は PUT /me/profile を 410 で断る(Go の PR #18。本番の DB にマイグレーション 00002 を当ててから、Go を出す)
- 宛先ごとの制限は、他人のログインを妨害するのに使える(+ のエイリアスは別に数える)
- CSP の退行(静的なページを足すと nonce が付かず止まる)を自動では検知できない
- Cron の DELETE に件数の上限がなく、CRON_SECRET の最小長も強制していない
- 見送ったレビュー指摘: encryptOAuthTokens と storeToken: "hashed"、メール HTML の URL のエスケープ
- Vercel のプレビューのビルドは失敗する(環境変数が Production だけ。使わない方針)
- 無料プランの Render はスリープする。スリープ明けの初回は 5 秒で切れて bio が出ないことがある
