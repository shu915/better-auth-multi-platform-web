今回の変更(git diff)を評価し、合格か要修正かを判定してください。
tsc・lint・テストは Stop hook(`.claude/hooks/stop-checks.sh`)が毎回実行し、失敗していれば差し戻される。ここでは重複して実行しない。
評価は「ビルド確認」と「コードレビュー」の2段階で行います。

## 進め方
1. `git diff` と `git status` で変更範囲を確認する(未追跡ファイルも含める)。
2. `npm run build` を実行して結果を記録する(`.next/` ができる副作用は許容する)。hooks の対象外なのでここで確認する。
3. ビルドが失敗したら、レビューより先に「高」の指摘として挙げる。
4. テストの改ざんを確認する(下の「改ざんの検出」)。
5. 今回変更されたファイルと、その呼び出し元・呼び出し先を読み、下の観点でレビューする。

## 改ざんの検出
検証が通っていても、通すためにテストや値を弱めていれば不合格にする。`git diff` の `*.test.ts`、`eslint.config.mjs`、`tsconfig.json`、`vitest.config.mts` と、設定値の差分を読み、次を探す。
- 削除されたテストやテストケース、新しく足された `it.skip` / `test.skip` / `it.todo` / `.only`、`exclude` による除外
- 期待値やアサーションが、仕様の変更ではなく実装の出力に合わせて書き換えられている(厳密な比較が `toBeDefined` や `toBeTruthy` に緩む、期待するステータスやメッセージが変わる、など)
- `// @ts-ignore`、`// @ts-expect-error`、`any`、`as unknown as`、`eslint-disable` を、理由なく足して通している
- tsconfig や ESLint のルールを緩めて通している(`strict` を外す、ルールを `off` にする、など)
- タイムアウト、上限値、許可リストなどが、理由なく緩められている
- 実装を直さず、テスト側のモックや入力だけを変えて通している
見つけたら、他の指摘より先に「高」として挙げ、元の内容(差分の該当箇所)を引用する。仕様変更が理由なら、その根拠が差分や説明にあるかを確認し、なければ指摘する。

## レビュー観点
1. 【セキュリティ】:認可漏れ(Server Action と Route Handler でセッションを確認しているか)、インジェクション・XSS(メール HTML の URL のエスケープなど)、機密情報の露出(`NEXT_PUBLIC_` に秘密を入れていないか、JWT やトークンをブラウザに出していないか)、レートリミット
2. 【パフォーマンス】:N+1問題、不要な再計算/再レンダリング、過剰なDB/API呼び出し、Client Component にする必要のないものを `"use client"` にしていないか
3. 【エッジケース・異常系】:null/undefined/空配列、外部連携(Go API、メール送信)のタイムアウトやエラー時の挙動(API が落ちても画面全体を壊さないか)
4. 【データ整合性・冪等性】:連打による二重処理の防止(フォームの二重送信、Server Action の重複実行)、トランザクションのロールバック漏れ
5. 【メンテナンス性】:命名の意図、関数の責務分割、型定義の厳密さ(`any` を使っていないか、Go の API レスポンスの型と一致しているか)

プロジェクトの方針は `CLAUDE.md` と `AGENTS.md` に従う。特に次を確認する。
- Go API の呼び出しはサーバー側(`callApi`)だけで行い、JWT をブラウザに出さない。フォームは Server Action 経由にする
- このリポジトリの Next.js は、学習済みの知識と違う場合がある。Next.js の API の使い方を指摘するときは、先に `node_modules/next/dist/docs/` の該当ドキュメントを読んで確認する(推測で「非推奨」「誤り」と言わない)
- `.env` 系のファイルは読まない(PreToolUse hook でもブロックされる)

## 制約
- コードは書き換えない。指摘と修正例の提示だけを行う。
- ファイルの編集、コミット、マイグレーション(`db:migrate`)の実行、`db:schema` による `src/db/schema.ts` の再生成はしない。
- ビルドの実行で生じるキャッシュや `.next/` などの副作用は許容する。
- 推測で指摘せず、コードを読んで確認できたものだけを挙げる。

## 判定
- **合格(LGTM)**: ビルドが通り、「高」「中」の指摘がない。
- **要修正**: ビルドの失敗、テストの改ざん、または「高」「中」の指摘が1つでもある。
- `npm run build` は、環境変数が未設定(例: 本番ビルドでは `BETTER_AUTH_URL` が必須)で失敗することがある。失敗の原因がコードではなく環境変数の不足なら、「要修正」にはせず、原因を明記して未検証として報告する。コードの型エラーやビルドエラーなら、通常どおり不合格にする。
- テストが少ない部分(画面や E2E は対象外)は、「通った」とみなさない。検証していない範囲を未検証として明記する。

## 出力形式
最初に判定を1行で書く:`判定: 合格` または `判定: 要修正`。

続けて、次の順に書く。
1. ビルドの結果(コマンド / 結果 / 備考)。tsc・lint・テストは hook が検証済みと一言添える
2. 指摘の一覧。指摘ごとに、重要度(高/中/低)、観点(1〜5)、場所(`ファイル:行`)、理由、修正コード例を書く。
3. 未検証の項目(ビルドの環境変数不足、画面のテストなし など)

指摘が1つもなく、検証もすべて通り、未検証もない場合は「LGTM」とだけ答える。
